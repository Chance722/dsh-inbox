# 同步机制：推什么、什么时候推、拉回来怎么合

2026-09-20 用户问"上传下载这一套是不是该沉淀一份文档"——该。布局的含义在 `remote-sync-layout.md`，本文讲**机制**：什么时候动、动什么、冲突怎么办、错了怎么查。

## 一句话

**两个方向、三种触发、一个真相来源**：推送把本机记录与附件写进 `sync/`；拉取读两处——你放东西的**投放目录**（`inbox/`）与**同步包**（`inbox/sync/`）；`items/<id>.json` 是唯一真相，`.txt` 只是给人看的视图。

## 什么时候动

| 触发 | 推送 | 拉取（投放目录 + 合并） |
|---|---|---|
| 入库 / 改动后 | ✅ 防抖 5 秒自动推一次（连着存五条只推一次） | — |
| 服务启动 | — | ✅ 后台一次（不阻塞启动、失败不影响启动） |
| 面板「刷新」（= 同步） | ✅ 先推 | ✅ 再拉（并合并）+ 重读列表 |
| 全量重传（只留接口） | ✅ 忽略游标全重推 | — |

**推送是自动的**：入库或改动后防抖 5 秒推一次（失败静默——按一次「刷新」就能看到真实结果）。**「刷新」就是同步**：先推本机改动、再拉别人的、然后重读列表；配置面板里不再有「立即同步 / 立即拉取 / 全部重传」三个按钮（前两个与「刷新」重复，第三个是修故障用的，走接口 `push {"all":true}`）。

## 推什么

- 一条记录 → `sync/items/<记录 id>.json`（`{format:"dsh-inbox-item/1", record}`）+ `<记录 id>.txt`（可读视图）。
- 它引用的每个附件 → `sync/attachments/<附件 id>.<扩展名>`（字节）+ `<附件 id>.meta.json`（元数据行：mime/字节数/原文件名/宽高/sha256）。
- **增量靠游标** `global.sync.lastPushAt`：只推 `updatedAt` 比它新的记录；附件跟着记录推（内容寻址，同一份字节只传一遍）。
- **软删的记录照推**（带 `deletedAt` 墓碑），这样别的设备才知道它被删了。

## 拉回来怎么合（2026-09-20 起已经能做）

1. 列 `sync/items/`，只看 `<uuid>.json`（文件夹占位、`.txt`、别的插件留下的东西一律不读）。
2. 按 **`id` 对齐**，按 **`updatedAt` 判胜负**：远端更新 → 覆盖本地；本地更新或相等 → 保留本地。
3. 新记录**原样写入**（保留 id / `createdAt` / `updatedAt`）——不能重新盖时间戳，否则两边会永远来回覆盖。
4. 记录需要的附件在本机没有 → 读 `<id>.meta.json` + `<id>.<ext>`，交给 dsh 的附件仓库准入（图片走图片准入），行 id 用远端的，`storeId` 用本机新分配的——这样记录里的 `attachmentIds` 仍然指向得东西。
5. **没有冲突副本**：用户明确要求"直接覆盖"。

## 上云加密边界（用户 2026-09-20 决定）

只有**账密正文**是密文（`secret` 字段）。文本、链接、标题、备注、类目、标签、时间、附件字节都是**明文**——**远端必须有访问控制**。主密码与派生密钥**永不上传**；账密记到另一台设备上是密文，那台设备没有同一个主密码就读不出来（`secretText` 返回 undefined，界面显示"正文是密文"）。

## 错了怎么查

| 症状 | 先看哪里 |
|---|---|
| 推了但桶里没有 / 变了 0 字节 | 「自检」的 LIST 行（摘录 400 字符，含 `<Key>` 与 `<Size>`）；「全部重传」再试一次 |
| 认证被拒 | 自检结论 + `remote-gateway-compat.md`（客户端标识按凭证绑定） |
| 拉取 `failed: N` | 现在会带文件名与原因（前三条）；`sync/` 下的东西永远不算"投放文件" |
| 另一台设备的记录没出现 | 「立即拉取」看 `merged` 数：0 说明它没推过、或两边 `updatedAt` 相同 |
| 桶里出现 0 字节的 `…/` 对象 | 云盘自己建的目录占位，不是插件 |
| 提示「还发现另一套同步前缀 …（本机是 …）」 | 见下面两节：**目录的三种写法是同一个意思**，以及 **S3 那条曾经误报的 bug** |

## 「目录」的三种写法是同一个意思（2026-09-21 明确）

`设置` 里的「目录」经过 `syncDirectory()` 归一：**留空、`/`、`inbox`（以及 `inbox/`）全都等于 `inbox`**。
所以两台机器只要都用这几种写法之一，就是同一套目录，不会"设置不一致"。真正的同步根是 `<目录>/sync`（默认 `inbox/sync`）。

历史坑：更早的版本里，`/` 在**写**的那一侧被当成了桶根（`sync/`），而**读**的那一侧早就按 `/inbox` 理解——
于是两台机器各自写在两个地方，互相看不见。这就是现在这条统一规则存在的原因，也是远端可能同时留着
`sync/…`（旧版写的）与 `inbox/sync/…`（现在写的）两套对象的原因。**根目录那套 `sync/` 是遗留物**，
不再被扫到；确认里面没有别的东西后，可以在云盘控制台里删掉。

## 提示里的数字是什么意思（2026-09-21 改）

拉取那行现在这么说：`拉取完成：云端有 {记录} 条记录 / {附件} 个附件（远端共列出 {对象} 个对象）…`。

- **记录 / 附件**：云端真正存了多少东西——`items/<id>.json` 的个数，以及 `attachments/<id>.<ext>`（不含 `.meta.json` 描述文件）。
- **对象**：S3/WebDAV 列出来的文件个数。一条记录至少占两个对象（`.json` + `.txt`），带图再加附件与它的 `.meta.json`，
  所以对象数天然是记录数的两三倍。用户当时的原话是「远端 78 项，可我并没有那么多东西」——现在不用自己换算。

### 附带修掉的一个真 bug：S3 把「自己的根」传错了（2026-09-21）

`pullDropFolder` 的 S3 分支原来把 `settings.directory.replace(/^\//,'')` 既当**列举前缀**又当**自己的同步根**传给 `pullS3`。
后果有两条，用户都撞上了：

1. `settings.directory` 是 `/` 时前缀变成空串 ⇒ **列了整个桶**（78 个对象，把根目录那套遗留 `sync/` 也扫进来）；
2. 自己的根成了 `''`（或 `inbox`）而不是 `inbox/sync` ⇒ **每一个自己的对象都被判成"别人的前缀"**，
   于是提示「自己的同步对象 0 项」+「还发现另一套同步前缀 sync、inbox/sync」，而其中一套根本就是本机的。

WebDAV 那半边一直是对的（它用 `syncDirectory` 列举、用 `syncRootFor` 认自己的树）。修法：S3 走同一条规则——
列举 `<目录>/`，自己的根用 `syncRootFor(目录)`。真机复验（用户自己的桶）：
**修前** `listed 78 / skipped 78（自己的 0、更远的 76 被当成别人的）`；**修后** `listed 24 / skippedSync 23 / skippedForeign 0 / remoteRecords 7 / remoteAttachments 3`，
「另一套前缀」的警告消失。

## 删除的两种意思（2026-09-20 起都完整了）

| 动作 | 本地 | 云端 |
|---|---|---|
| **软删**（面板里「删除」） | 进回收站 | 墓碑随下一次推送上去，别的设备因此知道它被删了 |
| **清空回收站** | 真删记录与无人引用的附件行 | **同步删掉对应对象**：`items/<id>.json`、`.txt`、以及只被它引用的附件的字节/元数据/旧命名对象 |

清空回收站是**定向删除**：只删你刚刚清掉的那些记录的东西，绝不"清扫"本地没有的远端对象——那会把别的设备推来、本机还没合并的记录当成垃圾。

## 还没做（写在这里免得误判）

1. **推送不自动化**：没有"粘贴后自动上云"，也没有定时推送；要上云就点「立即同步」或「全部重传」。
2. **拉取失败会自动重试**（已修）：游标只推进到最新**成功**条目，失败的那条下一次还会再试；重复入库会被合并掉，安全。
3. **多设备同一条同时改**：按 `updatedAt` 后写赢，可能丢一边的改动（用户拍板不留冲突副本）。
