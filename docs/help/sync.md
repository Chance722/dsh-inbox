# 同步机制：推什么、什么时候推、拉回来怎么合

2026-09-20 用户问"上传下载这一套是不是该沉淀一份文档"——该。布局的含义在 `remote-sync-layout.md`，本文讲**机制**：什么时候动、动什么、冲突怎么办、错了怎么查。

## 一句话

**两个方向、三种触发、一个真相来源**：推送把本机记录与附件写进 `sync/`；拉取读两处——你放东西的**投放目录**（`inbox/`）与**同步包**（`inbox/sync/`）；`items/<id>.json` 是唯一真相，`.txt` 只是给人看的视图。

## 什么时候动

| 触发 | 推送 | 拉取（投放目录 + 合并） |
|---|---|---|
| 入库 / 改动后 | ✅ 防抖 5 秒自动推一次（连着存五条只推一次） | — |
| 服务启动 | — | ✅ 后台一次（不阻塞启动、失败不影响启动） |
| 面板「刷新」（= 同步） | ✅ 先推 | ✅ 再拉（并合并）+ 重读列表 |
| 全量重传（只走接口，**界面上没有按钮**） | ✅ 忽略游标全重推 | — |

**推送是自动的**：入库或改动后防抖 5 秒推一次（失败静默——按一次「刷新」就能看到真实结果）。**「刷新」就是同步**：先推本机改动、再拉别人的、然后重读列表；配置面板里不再有「立即同步 / 立即拉取 / 全部重传」三个按钮（前两个与「刷新」重复，第三个走接口 `push {"all":true}`）。

> **2026-10-08 复查，「全部重传」的按钮没有加回来（用户拍板）**：游标那条规则修好之后（见「推什么」里的「失败的事不会被丢掉」），一次推送里失败的东西会被**下一次「同步」自动重试**——所以界面上那颗「同步」已经把这个功能覆盖了，不需要第二个入口。
> `push {"all":true}` 因此只剩一种用途：捞回**在这次修复之前就已经掉队**的记录（游标早已越过它们，重试规则救不回来）。实测那次是 5 条 9/19–9/21 的记录；除了走接口，**把那条记录改一下再保存**同样能把它重新推上去（保存会刷新 `updatedAt`）。

## 推什么

- 一条记录 → `sync/items/<记录 id>.json`（`{format:"dsh-inbox-item/1", record}`）+ `<记录 id>.txt`（可读视图）。
- 它引用的每个附件 → `sync/attachments/<附件 id>.<扩展名>`（字节）+ `<附件 id>.meta.json`（元数据行：mime/字节数/原文件名/宽高/sha256）。
- **增量靠游标** `global.sync.lastPushAt`：只推 `updatedAt` 比它新的记录；附件跟着记录推（内容寻址，同一份字节只传一遍）。
- **失败的事不会被丢掉**（2026-10-08 修）：一次推送里只要有记录没写完整（记录 JSON 写失败、或它的附件没上去），游标就**只推进到那条之前**，下次推送自然会把它们再送一遍（覆盖写，幂等）。修之前它是"只要有一条成功就跳到 `now`"，于是"一条成功 + 一条失败"就**永久吃掉**失败那条——用户实测的 5 条孤儿记录（只存在于一台机器、两端在用数 38 vs 33）就是这么攒出来的，而且面板还显示「最新」。唯一的例外是那条可读的 `.txt` 视图：它是每次推送重生成的视图、JSON 才是真相，所以它坏了**不钉**游标——否则遇到一个不喜欢 `text/plain` 的网关，每次同步都会把整段增量重传一遍。
- **软删的记录照推**（带 `deletedAt` 墓碑），这样别的设备才知道它被删了。

## 拉回来怎么合（2026-09-20 起已经能做）

1. 列 `sync/items/`，只看 `<uuid>.json`（文件夹占位、`.txt`、别的插件留下的东西一律不读）。
2. 按 **`id` 对齐**，按 **`updatedAt` 判胜负**：远端更新 → 覆盖本地；本地更新或相等 → 保留本地。
3. 新记录**原样写入**（保留 id / `createdAt` / `updatedAt`）——不能重新盖时间戳，否则两边会永远来回覆盖。
4. 记录需要的附件在本机没有 → 读 `<id>.meta.json` + `<id>.<ext>`，交给 dsh 的附件仓库准入（图片走图片准入），行 id 用远端的，`storeId` 用本机新分配的——这样记录里的 `attachmentIds` 仍然指向得东西。
5. **没有冲突副本**：用户明确要求"直接覆盖"。
6. **本机没有这条时先问墓碑**：`graves` 里记着这个 id 被清空的时刻，云端副本不比它新就不收（理由与边界见下面「清空之后为什么不会再回来」）。

## 上云加密边界（用户 2026-09-20 决定）

只有**账密正文**是密文（`secret` 字段）。文本、链接、标题、备注、类目、标签、时间、附件字节都是**明文**——**远端必须有访问控制**。主密码与派生密钥**永不上传**；账密记到另一台设备上时，用**封它的那个密码**才读得出来（两台机器各设过密码就各解各的，见下一节；`secretText` 返回 undefined 时界面显示"正文是密文"）。

> 按钮改名（2026-10-02）：面板上那个按钮现在叫 **「同步」**（原来叫「刷新」）。它一直是"先推后拉再重读列表"的完整同步，名字却像个本地重载，用户提出后改正。**下文历史段落里的「刷新」都是同一个按钮**，保留原话不改写。

## 主密码参数随同步走（2026-10-01 修，用户报的 bug）

**症状**：另一台机器存了 7 条账密，这台机器同步过来后看不了——面板说「还没设主密码」，点「设置 / 更换」却回一句「仓库里已有 7 条密文，但现在是锁定状态」。两条路都堵死。

**根因**：密钥由主密码 **scrypt** 派生，而 scrypt 要**盐**。盐只存在 `global.master` 里，而 `global.master` 从来不参与同步（推送只写 `items/`、`attachments/`）——所以第二台机器拿到的是**没有配方**的密文，**连正确的主密码都派不出那把钥匙**。"上云只有密文"这条红线被实现成了"只传 `secret` 字段"，把配方也一起留在了第一台机器上。

**修法**：推送多写一个 **`sync/master.json`**（`{format:"dsh-inbox-master/1", master:{version,salt,kdf,verifier}}`），合并时手里有密文就去取回来。此后面板说的是「有 N 条密文，解锁参数还没到本机」，正文一句"先点一次「同步」把参数拉回来，再输原来那台机器的主密码"。

**第二步（2026-10-02，用户定的规则：各解各的）**：光是"同步参数"还不够——两台机器**各自设过密码**时，谁也不能覆盖谁。所以：

- 域里多一组 **`global.masterOthers[]`**：`master` 仍是**本机自己加封新记录用的**那套，别的机器那套并列存在，只用于"解"。
- 内存里也从"一把钥匙"变成**钥匙串**（`salt → key`）。`unlock(密码)` 对**每一套已知参数**各派生一次、各验一次 verifier，命中就留下那把钥匙。于是：输自己的只解自己的，输对方的只解对方的，两边**同一个密码**就一次命中两套（不需要任何特殊处理）；两把钥匙可以同时握在手里。
- 读一条记录用手里几把钥匙**逐个试**（GCM 认证标签会明确否掉不匹配的），所以**记录里不需要记"这条是谁封的"**。
- 加封新记录优先用本机自己那把；本机从没设过密码（参数是从对方同步来的）时 `master` 本身就是对方的 ⇒ 等于"本机也认为已经设了主密码，和对方一致"。
- 换密码只重封**本机自己那把能开的**记录（`localKey()`），对方加封的不动——动了就等于把那批从对方手里拿走。锁定状态下继续拒绝换密码。

面板因此多一种状态（用户 2026-10-02 定的表）：

| 情形 | 面板 | 输密码后 |
|---|---|---|
| 本机没密码 + 拉到对方的密文和参数 | 「已锁定」 | 输对方的 → 那批解开（= 已设主密码） |
| 本机有密码 + 又拉到对方的 | 「已锁定」 | 输自己的 → 自己那批解开，卡片多一句「还有 N 条解不开：它们是另一个主密码加的密，输那个密码就能解开」；再输对方的 → 那批也解开（先输哪一边都一样，所以提示不写"那台机器"） |
| 两边密码相同 | 「已锁定」 | 输一次，两套 verifier 同时命中，无额外步骤 |
| 参数还没同步过来 | 「有 N 条密文，解锁参数还没到本机」 | 先点一次「同步」把参数拉回来 |

**域版本号刻意不动（仍 v8）**：`masterOthers` 是**可选**键，老插件读到只会静默丢掉；而 `dsh-storage-json` 是 `version !== descriptor.version` **严格相等**就抛 `version-mismatch`（读源码确认），升版本会让老插件——包括你另一个 profile 上那个 0.2.8——直接**打不开仓库**。代价只是老插件写一次 global 会把这一行丢掉，下次同步再补回来。

几条边界，都是刻意的：

- **上云的东西只有配方，没有密码**：`salt` 与 KDF 参数是算法公开的一部分（知道它不等于知道密码）；`verifier` 是**固定字符串的密文信封**，用来区分"密码不对"和"信封被改过"。增量风险为零——桶里本来就有密文正文，而 GCM 的认证标签本来就能拿来验一个密码猜得对不对。
- **本机已经有自己的 `master` 就不覆盖**：对方的进 `masterOthers`，两边都留着（覆盖 = 拿本机记录的可读性去换远端的）；本机没有密文就不读（没东西要解锁）。
- **取回参数不等于解锁**：`unlock()` 仍要人**显式输一次密码**；不输，仓库照样锁着。
- **取参数的时机在合并记录之后**：先问"本机有没有解不开的密文"，答案在记录落库之后才会从 0 变成 N——顺序反了就要拉第二次才生效（写这段时先踩了一次，已改）。
- **改密码要先解锁本机那把**：有密文而本机钥匙不在手里时 `setMasterPassword` 照旧拒绝（否则本机那批永远打不开）。
- **A 上换密码、B 会怎样**（2026-10-01 记的边界，2026-10-02 由上面第二步收口）：A 重新封一遍、推上去，B 按 `updatedAt` 覆盖成新密文；B 手里是 A 的**旧**参数，所以那批用新密码解不开——但 B **自己的**那批照旧能开（钥匙串里两把钥匙互不干扰），而且再同步一次会拿到 A 的新参数、追加进 `masterOthers`，A 的新密码就能在这边用了。历史参数不清理（一条记录由谁封的没记在记录上，删掉就没有退路）。

| 另一台设备的记录没出现 | 「立即拉取」看 `merged` 数：0 说明它没推过、或两边 `updatedAt` 相同 |

| 「我上传了，刷新后却没有 / 很久没同步过来」 | **先把远端量清楚**（整桶列一遍 + 看最新对象的时间），再谈"没同步"——见下面「上传了却看不到：先量远端」；常见的一半是**东西根本没进这个桶** |
| 清空回收站了，重启后又躺在回收站里 | 已修（域 v8 的 `graves`）：升级到 0.2.7 后**再清一次**就永久生效——在此之前清掉的那些没有墓碑记录。详见下面「清空之后为什么不会再回来」 |
| 桶里出现 0 字节的 `…/` 对象 | 云盘自己建的目录占位，不是插件 |
| 提示「还发现另一套同步前缀 …（本机是 …）」 | 见下面两节：**目录的三种写法是同一个意思**，以及 **S3 那条曾经误报的 bug** |

## 「目录」的三种写法是同一个意思（2026-09-21 明确）

`设置` 里的「目录」经过 `syncDirectory()` 归一：**留空、`/`、`inbox`（以及 `inbox/`）全都等于 `inbox`**。
所以两台机器只要都用这几种写法之一，就是同一套目录，不会"设置不一致"。真正的同步根是 `<目录>/sync`（默认 `inbox/sync`）。

历史坑：更早的版本里，`/` 在**写**的那一侧被当成了桶根（`sync/`），而**读**的那一侧早就按 `/inbox` 理解——
于是两台机器各自写在两个地方，互相看不见。这就是现在这条统一规则存在的原因，也是远端可能同时留着
`sync/…`（旧版写的）与 `inbox/sync/…`（现在写的）两套对象的原因。**根目录那套 `sync/` 是遗留物**，
不再被扫到；确认里面没有别的东西后，可以在云盘控制台里删掉。

### 换电脑、换目录、以及"这条要不要拉"（2026-09-21 回答用户三问）

**问题一：两台电脑都不配目录，能不能互相拉到？** 能。两边都归一成 `inbox` ⇒ 同步根都是 `inbox/sync`，
推送与合并读的是同一个地方。设置面板里现在也会实时显示这件事：目录输入框的占位符写着「inbox（默认；留空或 / 都等于它）」，
右边跟着「别的设备往这里扔东西 · 同步根：inbox/sync」。

**问题二：存到别的目录行不行？** 行——把「目录」设成 `backup`，**投放目录**与**同步树**一起搬过去
（`backup/` 与 `backup/sync`）。条件是**两台机器设成同一个值**。注意**改目录等于搬家**：旧目录里的东西不会自动搬，
要么两边同时改、要么先把旧目录的对象手工挪到新目录，否则新目录看起来"空的"（而这**不会**报错，会说"云端的记录没有新的"）。

**问题三（关键）：B 拉取时，怎么知道云端那条要不要拉回来？** 按**记录粒度**判，**不看"是谁上传的"**：

| 云端有什么 | B 本地的状态 | 结果 |
|---|---|---|
| `items/<id>.json`（A 推的，B 没有） | 没有 | **合并**（`merged`），带附件时连字节一起拉 |
| 同一条（B 自己推上去的，或之前已经合并过） | 同 id、`updatedAt` 相同 | **保留**（`kept`），不重复入库 |
| 同一条，A 后来改过 | 同 id、**更旧** | **合并**（严格更新才赢：`updatedAt` 比本机大） |

具体判据是 `wins()`：`Date.parse(remote.updatedAt) > Date.parse(local.updatedAt)`——严格更新才覆盖，
时间戳相等视为"两边一致"（自己推上去的记录回来时时间戳不变，所以不会反复覆盖自己）。
**所以不存在"目录是插件上传的就简单跳过"这种判断**，也不会：`sync/` 那半边一律不当投放文件入库，
真正的"要不要"由 merge 逐条比 id + `updatedAt` 决定。

面板现在把这三种结果都报出来，例如：

```
拉取完成：云端有 7 条记录 / 3 个附件（远端共列出 24 个对象），新入库 0 条，跳过 24 条 ·
（自己的同步对象 23 项、比上次拉取更旧 1 项） · 云端的 7 条记录本机都有
```

最后那句是 2026-09-21 新加的（`kept`）：**"没有新的"和"云端的副本就是我自己的"是两件事**，
以前它们看起来一模一样。

### 记录卡在"另一套目录"里怎么办（2026-09-21 用户真实场景）

现象：两台机器都说"没有新的"，家里那台明明推过东西。真机数字（用户自己的桶）：
`inbox/sync` 里 7 条记录、全部 `kept`（本机都有）——因为那些本来就是**本机自己推上去的**；
而桶根的 **`sync/` 里另有 19 条记录**，从来没人读它。

**为什么会有另一套**：更早的版本把「目录 = `/`」当成**桶根**，于是 `sync/`（而不是 `inbox/sync/`）成了同步树。
修掉那条规则之后，**目录之外的树一律不读**（这是对的：随便捡一个外来树，等于把别人的仓库合并进来）。
代价是"看不见"，所以现在补了一次**有界的探测**：

| 探测 | 怎么做 | 目的 |
|---|---|---|
| 桶根有哪些目录 | `delimiter=/` 一次列举（≤100 键），最多看 5 个候选 | 一次请求就知道"楼上还住着谁" |
| 某目录是不是同步树 | 每个候选查 `<目录>/sync/items/`，再退一步查 `<目录>/items/`（各一次，`max-keys=1000`） | 认出 `foo/sync`（换过目录）与桶根 `sync`（旧版布局）两种情况 |

命中的结果进 `foreignSyncRoots`，并数出 `foreignRecords`（那里面有多少条 `items/*.json`）。
**刷新按钮的 tooltip** 会写全（含"本机是哪个"），**toast** 只留一句短的：
`⚠️ 另有 19 条记录在别的同步目录：sync`。

**怎么把它们弄过来**（2026-09-21 起有开关了）：

**设置 → 同时合并别的同步目录**（默认关）。打开之后，刷新会把**同一个桶里所有被探测到的 `*/sync` 树**都当成合并来源，
逐条按 `id` + `updatedAt` 判新旧——也就是"整块云盘都是我的"这个直觉。真机（用户自己的桶）：
打开后一次刷新 `merged: 19`（`added: 6`）、`attachments: 6`，本机记录 **7 → 13 条**；
那 13 条"覆盖"是家里昨天推的副本比本机新，按规则它们赢了。

**为什么默认关**（写清楚，免得下次又有人问）：

1. **桶可能是共享的**：目录就是用来把两个仓库分开的；自动合并等于把别人的记录也吞进来。
2. **别人的树里那份副本我们不替你删**：清空回收站只删**本机那棵**同步树里的对象（`remote/remove.ts` 是定向删除，见下）。
   另一棵树里的对象属于"可能是别人的仓库"，删它不可逆 ⇒ 我们只**不读回来**，不代删。

> 2026-09-21 修掉的一条真 bug 就长在这两点之间：清空回收站之后，老树里那 13 条墓碑**每次重启都回到回收站**
> （因为清空之后本机什么都不留，merge 没有任何本地东西能压住它们）。现在靠本地墓碑 `graves` 挡住，见下一节。
> 默认关的理由因此只剩第 1 条 + "不代删别人树里的对象"。

另外两条老路仍然有效（不想开开关时）：**把两边目录改成同一个**再让旧那台全量重推；
或者**在云盘控制台里把对象挪到 `inbox/sync/`**（结构一一对应，文件名不用改）。

**数字口径**：`merged` 是"从远端取过来的记录条数"（含覆盖同 id 的旧副本），`added` 是"其中本机原先没有的"。
真机上这两个是 19 / 6，所以面板写「拉取 19 条（其中 6 条是新记录）」——列表增长对得上那个 6。

**顺带说明**：`foreignRecords` 只是"我们看到的那些树里有多少条记录"，不是"一定有这么多条要新入库"——
里面可能就是本机更早推上去的旧副本（合并时按 `id` + `updatedAt` 逐条判，重复的自然留在 `kept`）。

## 提示里的数字是什么意思（2026-09-21 改）

拉取那行现在这么说：`拉取完成：云端有 {记录} 条记录 / {附件} 个附件（远端共列出 {对象} 个对象）…`。

- **记录 / 附件**：云端真正存了多少东西——`items/<id>.json` 的个数，以及 `attachments/<id>.<ext>`（不含 `.meta.json` 描述文件）。
- **对象**：S3/WebDAV 列出来的文件个数。一条记录至少占两个对象（`.json` + `.txt`），带图再加附件与它的 `.meta.json`，
  所以对象数天然是记录数的两三倍。用户当时的原话是「远端 78 项，可我并没有那么多东西」——现在不用自己换算。
- **跳过（host 端仍然报，面板不再显示）**：2026-09-21 用户问过一次「更旧是什么含义」，随后说"跳过的这些不用提示出来了"——
  两半都是**正常状态**，放在 tooltip 里像新闻：`PullResult.skippedSync` / `skippedOlder` 照旧在接口里，供排查用。含义是：
  - **本机上传的** = `…/sync/…` 下本机自己写的同步对象（记录的 `.json`/`.txt`、附件与 `.meta.json`）。它们**永远不当投放文件读**，
    否则自己的上传队列会被当成"别人扔进来的文本"再入一次库；它们该不该合并由 merge 那半边按 `id` + `updatedAt` 决定。
  - **上次已收过的** = 投放目录里比**上次拉取游标**更旧的文件。游标 `lastPullAt` 只推进到最后一次**成功**处理的条目时间，
    所以"更旧"的准确含义是"上一次拉取（或更早）已经收过它了"——真机例证：那条就是 `inbox/微信图片_…jpg`，
    它早就成了仓库里「默认头像」那条记录的附件。没有时间戳的条目会被当成新的再试一次。

### 附带修掉的一个真 bug：S3 把「自己的根」传错了（2026-09-21）

`pullDropFolder` 的 S3 分支原来把 `settings.directory.replace(/^\//,'')` 既当**列举前缀**又当**自己的同步根**传给 `pullS3`。
后果有两条，用户都撞上了：

1. `settings.directory` 是 `/` 时前缀变成空串 ⇒ **列了整个桶**（78 个对象，把根目录那套遗留 `sync/` 也扫进来）；
2. 自己的根成了 `''`（或 `inbox`）而不是 `inbox/sync` ⇒ **每一个自己的对象都被判成"别人的前缀"**，
   于是提示「自己的同步对象 0 项」+「还发现另一套同步前缀 sync、inbox/sync」，而其中一套根本就是本机的。

WebDAV 那半边一直是对的（它用 `syncDirectory` 列举、用 `syncRootFor` 认自己的树）。修法：S3 走同一条规则——
列举 `<目录>/`，自己的根用 `syncRootFor(目录)`。真机复验（用户自己的桶）：
**修前** `listed 78 / skipped 78（自己的 0、更远的 76 被当成别人的）`；**修后** `listed 24 / skippedSync 23 / skippedForeign 0 / remoteRecords 7 / remoteAttachments 3`，
「另一套前缀」的警告消失。

## 投放目录不是一个文件（2026-09-21 修）

**用户报的**：点「刷新」，拉取那行是 `failed: 1`，原因写着

```
inbox：取对象失败：HTTP 500 — {"msg":"未知运行时异常","code":500}
```

**真机数字**：`listed: 39 / skippedSync: 38 / skippedOlder: 0 / remoteRecords: 12 / remoteAttachments: 5`。
39 项里 **38 项是本机自己写的同步对象**（`inbox/sync/…`），只剩 **1 项不在任何 `sync/` 树下**，
而它的名字就是投放目录名 `inbox`。换句话说：**被当成"投放文件"去读的那一条，就是目录本身。**

**它长什么样**：S3 没有目录，所以云盘控制台里建的文件夹就是**一个 key 以 `/` 结尾的占位对象**
（「桶里出现 0 字节的 `…/` 对象」那条早就记过，只是那时以为它只影响观感）。列举 `inbox/` 时它和普通对象一样被列出来，
而网关并不打算把它当文件服务——GET 它回 **500 `{"msg":"未知运行时异常"}`**，和 `remote-gateway-compat.md`
里 SigV2 那个 500 是同一句话（这个网关对它不提供的东西一律回这句）。

**为什么每次都失败、还一直是同一句**：拉取游标只推进到最后一次**成功**的条目（有意的，见下面「拉取失败会自动重试」），
所以这一条永远比游标新 ⇒ 每次刷新都重试一次、每次都失败；而失败还要盖住"到底有没有新东西"这句话。

**修法**（`src/host/remote/pull.ts` 的 `isFolder()`，在投放目录那一层按**形状**跳过、根本不去 GET）：

| 形状 | 例子 | 为什么是目录 |
|---|---|---|
| key 以 `/` 结尾 | `inbox/`、`inbox/sub/` | S3 的目录占位对象；WebDAV 的集合 href 也是这个形状 |
| 路径就是这次列举的投放目录 | `inbox` | 网关把被列举的前缀本身当成一条返回的写法 |

两者进 `skipped`，另外数进 `PullResult.skippedFolders`（面板不显示，和 `skippedSync` 一样只供排查）。
`…/sync/` 树里的判定不动：那半边的理由仍然是"自己的上传队列"。

**为什么不"读失败了就算了"**：这次网关回的是 500，但**回 200 + 空 body 的网关一样存在**——
那样占位对象会被当成一个空文本入一次库，列表里从此多一条莫名其妙的记录。**"目录不是文件"必须在"要不要读"之前判**，
不能等读出来再看结果。同理，也不做"按扩展名猜"（投放目录里本来就可以放没有扩展名的东西）。

**没实测到的那一半**：没有对真桶重放这次 GET（凭据不在手上），所以"占位对象的确切 key 是 `inbox/` 还是不带斜杠的 `inbox`"
是按上面的数字与失败名推断的。两种形状现在都跳，所以不影响结论；**下次刷新若 `failed: 0` 且 `skippedFolders ≥ 1`，就说明它是这一个**。

**验证**：`test/webdav.test.ts` 两条新测试分别钉住两半——WebDAV（`inbox/sub/`）与 S3（`inbox/` 与 `inbox`），
断言都是"**根本没发出那次 GET**"加 `failed: 0`（`skippedFolders` 各是 1 与 2）；改之前这两条会红（拿到 500 并报
`inbox：取对象失败…`，与用户看到的那一句逐字一致）。

## 上传了却看不到：先量远端，再谈"没同步"（2026-09-28）

**用户报的**："我升级到 0.2.8 了，然后在公司上传了一些照片（比如我的身份证），刚刚点刷新显示最新的 17 条，
但证件里没有看到我在公司上传同步的身份证。"

**先把本地和远端各自量一遍**（两条都只读：不动游标、不写库）：

| 量什么 | 实测结果 |
|---|---|
| 本机库 | 30 条记录，**其中 13 条在回收站**（`deletedAt` 全是 09-19 的老墓碑）⇒ 在册 **17 条**；最后一次写入 `2026-09-21T12:32Z` |
| 本机游标 | `lastPullAt` 是**当天**这次刷新（拉取确实跑过），`lastPushAt` 还停在 09-21 |
| 整桶对象 | 账号下只有 `duoyu-inbox` 一个桶；桶里共 36 个对象，**最新那个是 `2026-09-21T12:32:13Z`** |
| 投放目录 | `inbox/` 里**没有任何"投放文件"**：只有 4 个目录占位对象（`inbox/`、`inbox/sync/`、`inbox/sync/items/`、`inbox/sync/attachments/`）与本机自己的同步树（11 条记录） |
| 目录外 | 桶根有且只有一个对象：`IMG_9270.jpg`（09-19 上传，370 KB）——**在桶根，插件永远读不到** |

**结论**：**"刷新没看到" 和 "云端没收到" 是两件事，先把后者量掉。** 这一次是后者——最近一周没有任何对象进过这个桶，
所以本机"没有新东西"是**正确答案**：投放目录空着，桶里那 11 条记录本机全有。

**那片面的数字**：弹窗里 `· 本页 17 条` 是**当前列表的在册条数**（30 条 − 回收站 13 条），不是"新到了 17 条"；
"新到几条"只看 `拉取 N 条`。两个数长得像，结论却相反，写在文档里免得下次又对不上。

**两条会让人"上传了却看不见"的硬规则**（是设计，不是故障）：

1. **只读 `inbox/`**：`目录` 的 `/`、留空、`inbox` 全都归一成 `inbox`（2026-09-21 定的规则，见上文），
   **桶根与别的文件夹不在任何配置的可读范围里**——往桶根或别的文件夹上传（就像那张 `IMG_9270.jpg`）＝永远看不见。
2. **另一台设备的方向**：照片若是在**另一台机器上用插件捕获**的，那台机器的**推送必须先成功**才谈得上本机拉得到
   （推送失败是静默的：只有点一次「刷新」或看它的 `inbox_status` 才知道）。本机拉不到"云端没有的东西"。

**只读排查手法**（下次直接用，别再猜）：

- 第一选择是**要数字**：当事人点「刷新」的 `pull` 返回值（`listed / skippedSync / skippedOlder / remoteRecords /
  foreignSyncRoots / reason`）或「自检」的 LIST 摘录，都不必碰凭据。
- 要看全，就用本包自己的客户端做一次**只读**列举：`listPrefix(config, '', deps)` 列**整桶**（能发现"传到了目录外"），
  `signRequest({ ...config, bucket: '' }, deps, 'GET', '')` 列**账号下的桶**（能发现"传到了别的桶"）。
  凭据在本机 `%DSH_HOME%\.credentials.yaml` 的 `DSH_INBOX_S3_SECRET`：**只读、只用于签名、绝不打印、绝不写进任何文件或提交**；
  这两步只 LIST，不写对象、不动游标。本次实测（用户自己的桶）：整桶 36 个对象、最新 `2026-09-21T12:32:13Z`、目录外仅那张 `IMG_9270.jpg`。

**顺带看到的**：那 13 条老墓碑此刻正躺在回收站里（`deletedAt` 全是 09-19）；桶根那棵遗留 `sync/` 已经不在了
（`listTopLevel` 只返回 `inbox`），所以在 0.2.8 上**再清一次回收站**就能永久清掉。

**产品上的空白（还没做）**：现在"云端没有新东西"和"云端根本没收到"在界面上长得一模一样——面板只报
「云端 N 条记录 / M 个附件」，**不报时间**。加一句「云端最新一条：X（N 天前）」就能当场分辨；这是下一步值得做的诊断性改进。

## 删除的两种意思（2026-09-20 起都完整了）

| 动作 | 本地 | 云端 |
|---|---|---|
| **软删**（面板里「删除」） | 进回收站 | 墓碑随下一次推送上去，别的设备因此知道它被删了 |
| **清空回收站** | 真删记录与无人引用的附件行 | **同步删掉对应对象**：`items/<id>.json`、`.txt`、以及只被它引用的附件的字节/元数据/旧命名对象 |

清空回收站是**定向删除**：只删你刚刚清掉的那些记录的东西，绝不"清扫"本地没有的远端对象——那会把别的设备推来、本机还没合并的记录当成垃圾。

### 清空之后为什么不会再回来（2026-09-21 修的真 bug）

**用户报的**：清空回收站 → 刷新页面确实是空的 → **关掉服务、重启 dsh，那 13 条又躺在回收站里**。

**原因不是删除失败，是"删不着那棵树"**。本机那棵同步树（`inbox/sync`）里的对象确实删掉了；
但同一个桶里还有一棵更早的 `sync/`（旧版本把 `/` 当桶根写的，见上文），里面躺着同样这 13 条**墓碑**的副本。
用户开着「同时合并别的同步目录」，于是每次**启动拉取**都会把老树当合并来源，逐条走 `wins()`——
而清空之后本机**一行都没有**了，`wins(remote, undefined)` 恒真 ⇒ 13 条墓碑原样导入 ⇒ 又躺在回收站里。
页面刷新不会触发拉取（只有「刷新」按钮与启动会），所以中间那一步看起来"明明清干净了"。

**修法：清空时留下本地墓碑 `graves`（域 v8）**——`vault.purge(id)` 删掉记录与附件行之后，再写一条 `{ id, purgedAt }`。
merge 在"本机没有这条"的分支里多做一次比较：

| 云端的副本 | 结果 |
|---|---|
| `updatedAt` **不比** `purgedAt` 新（老树里的旧副本、没拉过墓碑的设备推回来的） | **不收**（进 `PullResult.purged`，tooltip 写"清空过 N 条：云端的旧副本没有拉回来"） |
| `updatedAt` **比** `purgedAt` 新（别的设备在清空之后真的改过它） | **照旧赢**，按 `updatedAt` 规则合并——那是一次真改动，不是复活 |

三条边界值得记住：

- 墓碑是**本机事实**，不上云、不同步；别的设备各记各的。它只有 id + 时刻，没有正文、没有附件。
- **墓碑永不清理**（刻意的）：清掉一条墓碑等于把洞重新打开——那份副本的时间戳没变，下一次拉取照样收下它。代价是每条清空过的记录留一行 JSON。
- **远端另一棵树里那份副本不会被删**（定向删除只覆盖本机那棵树）：它留在云盘上，只是再也进不来。
  想清理它，在云盘控制台里删那棵树——但要先确认里面没有别的东西。
- 清空**之后**同一份内容再粘进来，是一条**新记录**（新 id、新时间），不受墓碑影响：墓碑只按 id 认人。

**验证**：`test/merge.test.ts`「keeps an emptied record out, even when another tree still holds a copy」钉住两半
（旧副本被拒 + 更新的副本仍然赢），`test/vault.test.ts` 钉住"记录文档真的没了、只留下 `graves/<id>.json`"，
外加一条"用域 v7 写的库能被 v8 打开"（版本加表不能毁掉任何人的库）。

## 还没做（写在这里免得误判）

1. **推送没有定时兜底**（自动推送本身早已落地，见上文「什么时候动」）：入库/改动后防抖 5 秒推一次，但服务没跑就不推，也没有按小时的兜底推送。（这一条 2026-10-01 订正：原文还写着"推送不自动化"，和本文自己的表格矛盾。）
2. **拉取失败会自动重试**（已修）：游标只推进到最新**成功**条目，失败的那条下一次还会再试；重复入库会被合并掉，安全。
3. **多设备同一条同时改**：按 `updatedAt` 后写赢，可能丢一边的改动（用户拍板不留冲突副本）。
4. **换主密码**（2026-10-02 已实现，见上文第二步）：B 拉一次就会拿到 A 的新参数并追加进 `masterOthers`，A 的新密码在这边照样能用；`masterOthers` 里的历史参数不清理（记录上没记"谁封的"，删掉就没有退路）。本机自己的密码改成别的：先解锁、再换，只重封自己能开的那批。
5. **WebDAV 拉取附件拿不到元数据**（2026-10-01 只读审查发现，未修）：`merge.ts` 读附件元数据时**手拼路径** `…/attachments/<id>.meta.json`，而 `SyncTree.read` 只认**列表给回来的**路径（S3 是 key，WebDAV 是服务器自己的 href），所以 WebDAV 上那次 read 会以 `Failed to parse URL` 失败 ⇒ 附件整条不入库（S3 不受影响）。同一个形状刚在 `master.json` 上修过（`findMasterObject()`，见上文），附件这处是更早留下的，改法同形：用现成的 `attachments/` 列表里那份 `.meta.json` 条目当路径。
