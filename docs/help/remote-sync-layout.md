# 远端目录布局（`inbox/` 里那些名字是什么意思）

2026-09-20 用户看着自己的桶问"这些目录名什么含义"，说明这套命名只活在代码和我脑子里——写下来。

## 一张表

假设设置里的「目录」填的是 `/inbox`（默认值）。桶里会长这样：

| 路径 | 谁写的 | 是什么 |
|---|---|---|
| `inbox/` | 云盘 UI | 目录占位对象（key 以 `/` 结尾、0 字节）。S3 没有目录，是网盘界面为了显示文件夹而建的，**不是插件写的** |
| `inbox/<你扔的文件>` | **你 / 别的设备** | M6 的**投放区**：任何设备往这一层扔文件，本机拉取时读它们并入库（读完不删，靠"已见"游标跳过） |
| `inbox/sync/` | 插件（推送） | 本机自己上传的东西。**与投放区刻意分开**——拉取就是"读投放目录"，两者混在一起的话，下一次拉取会把自己的同步包当别人扔的文件再入库一遍，而且每次拉取都来一遍 |
| `inbox/sync/items/<记录 id>.json` | 插件 | **一条记录一个文件**。`<记录 id>` 就是本地那条记录的 id（UUID，与本地 `storages/dsh_inbox/items/<id>.json` 同名）；反复 PUT 同一个 id 就是"更新这条" |
| `inbox/sync/items/<记录 id>.txt` | 插件 | **同一记录的「可读视图」**：标题、类目/类型/来源、时间、平台、标签、待看、链接、备注、正文，以及它引用哪些附件对象。**只为给人看**，拉取时从不读它（真相永远在旁边的 `.json` 里）；每次推送重新生成 |
| `inbox/sync/attachments/<附件 id>.<扩展名>` | 插件 | 附件**字节**。文件名是我们在 `attachments` 表里给该附件生成的 UUID **加一个由 mime 推出的扩展名**（`image/jpeg → .jpg`、`video/mp4 → .mp4`…推不出来就用 `.bin`）。**故意不用 `sha256:…` 那种 storeId**（冒号在路径/URL 里不安全，这也是本地那条"store id 不能当 key"的老坑） |
| `inbox/sync/attachments/<附件 id>.meta.json` | 插件 | 这个附件的**元数据行**（mime、字节数、原文件名、宽高、sha256）。没有它，别的设备能下载到文件却重建不出引用它的记录 |

一个 `items/*.json` 的内容是一个信封：

```json
{ "format": "dsh-inbox-item/1", "record": { "id": "…", "kind": "link", "category": "article", … } }
```

`record` 就是本地那条记录的字段（类目、备注、标签、时间、`linkTitle`、软删标记 `deletedAt`…）。

## 为什么这样命名

- **一条一文件**：增量就是"哪些文件变了"，而不是"整包重传"；一次失败只影响一条。
- **文件名 = 我们的 id**：远端对象的身份与本地记录一一对应，幂等覆盖，排查时能直接对号入座。
- **附件内容寻址**：同一份字节在本地只存一份、上传也只传一份（两条记录引用同一附件时仍是一个对象）；文件名用我们的行 id 而不是内容摘要，纯粹因为路径安全。
- **扩展名不是装饰**：最早的版本把附件写成"纯 id 无扩展名"，结果云盘里全是认不出的文件——用户直接问"我的图片呢？怎么都是 json？"。**对象的名字要让人（和别人的软件）看得出它是什么**。

## 为什么每条记录有两个文件（`.json` + `.txt`）

`.json` 是**给程序看的**：字段完整、无损，是同步的唯一真相来源。`.txt` 是**给人看的**：你在云盘里直接点开就能读那条记录——存的文章正文、这条链接是什么、两张照片分别属于哪条记录。两者都由推送生成，`.txt` 从不被读回。

- 账密记录的 `.txt` **只有一句"正文已加密"**，正文（密文）只在 `.json` 的 `secret` 字段里；备注照旧是可读的（它是用户自己的字，且 `.json` 里本来就是明文）。
- 视频/音频/PDF 等附件本来就是**可直接打开的字节**（`<id>.mp4`、`<id>.pdf`…），不需要文本视图；决定扩展名的顺序是**先用文件自己的原名**（`报税表.xlsx` 比任何表都懂它是什么），再按 mime 查表，最后才是 `.bin`。
- **`sync/` 独立**：见上表——它是"我们自己的东西"，和"别人扔进来的东西"必须能分开。

## 加密边界（和 `product-decisions.md` 的隐私红线一致）

| 内容 | 上云形态 |
|---|---|
| 账密记录的**正文** | `secret` 字段，密文信封 `v1:iv:tag:ct`（AES-256-GCM，主密码派生密钥） |
| 其他字段（标题、备注、链接、正文文本、类目、标签、时间） | **明文** |
| `attachments/*` 字节 | **明文**（附件里装着密钥，它就是明文） |
| 主密码 / 派生密钥 | **永不上传、永不同步** |

远端必须有访问控制：谁读得到桶，谁就读得到上面那些明文（这是 2026-09-20 用户明确选择的取舍）。

## 当前没有的东西

- **删除**（2026-09-20 起）：**清空回收站会连远端一起删**——`items/<id>.json`、`.txt`，以及只被它引用的附件的字节、`.meta.json` 与旧命名的无扩展名对象。软删仍然是墓碑（同步给别的设备）。定向删除，不做 sweep，而且**只删本机这棵树**：桶里另一棵老树（`sync/`）里的副本不动、也不代删，靠本机的 `graves` 挡住它们回来（2026-09-21，见 `sync.md`）。
- **合并已实现**（2026-09-20）：别的设备推到 `sync/items/` 的记录，本机拉取时会按 `id` + `updatedAt` 并进来（新的赢、没有冲突副本），需要的附件字节也会一起拉下来。机制见 `sync.md`。
- **改名的孤儿已清**：附件名从"纯 id"改成"id + 扩展名"留下的旧对象，会在推送该附件时被定向删掉（「全部重传」一次即可清完）。用户桶里那两只已经清掉了。
